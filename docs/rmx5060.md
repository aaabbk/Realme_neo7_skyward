# Realme Neo7（RMX5060）上的 Skyward

这台机器（MT6989 / 天玑 9300+，Android 14，A/B + virtual A/B）**没有独立的 recovery 分区**：它的 recovery 是 `vendor_boot` 里的一个 ramdisk 分片。所以 Skyward 不用「改原厂 recovery 再跑」，而是把需要的文件从原厂镜像里拿出来，组成**我们自己的 recovery**，写回 `vendor_boot` 的 recovery 分片。

## 1. `vendor_boot` 的结构（实测）

```
VNDRBOOT v4, 64 MiB 分区, 末尾 AVB footer
header(2128 B) → page 对齐 → vendor ramdisk 区 → page 对齐 → dtb(462,480 B)
                → page 对齐 → vendor ramdisk 表(2 × 108 B) → page 对齐 → bootconfig(0)

vendor ramdisk 区 = 两个各自 lz4_legacy 压缩的 cpio 分片顺序拼接：
  type=1 ""（platform）   40,308,964 B 压缩 / 110,309,120 B 解压，929 项
  type=2 "recovery"       12,270,023 B 压缩 /  26,505,728 B 解压，360 项
```

- 正常启动只加载 platform 分片；recovery 启动额外加载 recovery 分片。
- 内核按顺序解包，**后面分片里的同名文件覆盖前面的**（`init/initramfs.c` 的 `do_name()` 用 `O_TRUNC` 打开已有文件）。
- 因此：**platform 分片逐字节不动**（内核模块、first-stage 的 fstab 都在里面），只重写 recovery 分片。

## 2. 我们的 recovery 里有什么

清单在 `devices/rmx5060.recovery.toml`，由 `skyward-pack vendor-boot` 执行：

| 部分 | 内容 |
| --- | --- |
| 从原厂 ramdisk 取（`take`） | `system/bin/{init,ueventd,adbd,linker64,toybox,sh}`、`sepolicy`、各 `*_contexts` |
| 依赖闭包（`closure`） | 上面每个程序的 `DT_NEEDED` 递归补齐（实测 34 个库），**缺一个就构建失败** |
| 我们自己的 init 规则 | `crates/skyward-pack/recovery/init.rc`、`usb.rc`（gadget + adb） |
| Skyward | `system/bin/recovery`、`skyward/device.toml`、字体、`system-init`、`task_profiles.json`、`skyward-mtp.rc` |
| 手机自己的分区表 | `vendor/etc/fstab.mt6989`（`devices/rmx5060/fstab.mt6989`），super 为空时也能挂载 |
| 属性 | 原厂 recovery 的 `prop.default` + `ro.adb.secure=0`（recovery 内免授权 adb） |

**没有**：OPPO 的 phoenix_recovery、`res/` 资源、`sbin/*.sh`、任何 vendor 的 rc 脚本，也没有原厂的 `init.rc`。
`setenforce 0` 写在我们的 init.rc 里，因为这份 SELinux 策略不是为我们的 recovery 写的。

字体：`resources/fonts/MiSansVF.ttf` 有 20 MB，塞不进 64 MiB 的分区，用
`devices/rmx5060/subset-font.sh` 按 `crates/skyward-ui/locales/*.toml` 实际用到的字符做子集（883 KB）。

实测（NDK r29 aarch64 交叉编译的真实二进制）：

| 项 | 大小 |
| --- | --- |
| `skyward`（aarch64-linux-android，release） | 10,484,664 B |
| `system-init`（静态） | 1,040,664 B |
| 新 recovery 分片 | 15,752,153 B 压缩 / 31,300,288 B 解压 |
| vendor ramdisk 合计 | 56,061,117 B（原厂 52,578,987 B） |
| 分区（64 MiB）剩余 | 10,571,712 B |

`skyward` 只依赖 `libc.so`、`libm.so`、`libdl.so`，解释器 `/system/bin/linker64`，三者和解释器都在分片里
（构建时按 `DT_NEEDED` 递归取库，缺一个就失败）。

## 3. 构建

需要：`rust-toolchain.toml` 指定的 Rust（含 `aarch64-linux-android` target）、Android NDK r29 + `cargo-ndk`、`lz4`。

```sh
STOCK=vendor_boot.img sh devices/rmx5060/build.sh
```

`STOCK` 是这台手机自己的 `vendor_boot` 分区映像（整分区、末尾带 AVB footer）。
产出 `target/vendor_boot_skyward.img`，只有 recovery 分片变了。

## 4. 刷写与回滚

解锁 BL 之后，先关掉校验（否则 bootloader 不认改过的 vendor_boot）：

```sh
fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img
fastboot flash vendor_boot target/vendor_boot_skyward.img
fastboot reboot recovery
```

回滚（正常系统一直可用，因为 platform 分片没动）：

```sh
fastboot flash vendor_boot vendor_boot.img
```

## 5. 第一次开机的检查

1. 屏幕亮、出现 Skyward 首页 → display/DRM/背光链路通。
2. 能点 → `oplus_bsp_synaptics_tcm2` 在无 `touchDaemon` 时直接上报；否则先用按键。
3. `adb devices` 能看到、无需授权 → `usb.rc` 的 gadget 与 `ro.adb.secure=0` 生效。
4. `adb shell getprop sys.usb.controller` 应为 `11201000.usb0`；不对就改 `devices/rmx5060.recovery.toml` 的 `udc`。
5. 重启回系统，`adb shell getprop ro.adb.secure` 应为 `1` —— 证明 recovery 分片没有影响正常启动。
6. `reboot system` 能回系统。

## 6. 「没有系统也能开机」的验证

设计上，UI 启动路径不碰 super（`prepare()` 挂载失败只记 kmsg；`SystemProps` 容错；设置存 `/metadata`）。
硬证明只有把 super 清掉再开：**先完整备份 super**，`fastboot erase super`，进 recovery 应仍然出现 Skyward 界面，
之后再恢复 super。这一步有破坏性，确认备份可用再做。

## 7. 已知限制（下一步）

- **解密**：安全世界是 Trustonic（`mcDriverDaemon` + `keymint@3.0-service.trustonic`），
  `mcRegistry` 的 drbin 在原厂 recovery 分片里（可一并取），但 keymint 本体在 `/vendor`，需要单独抽取。
- **WLAN**：模块在 `vendor_dlkm`，固件与 `wpa_supplicant` 的库在 `/vendor`，暂不可用。
- **马达**：aw8697 是否支持 `FF_PERIODIC` 未知，未启用 `[haptics]`。
- **双系统 / 在线更新 / 「再次刷入 Skyward」**：都依赖 recovery 分区或 super，本移植暂不支持。
- **正常系统更新后**：整块 `vendor_boot` 会被覆盖，需要重新刷一次。
